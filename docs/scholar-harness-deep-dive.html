01 · 不夸大，也不低估

项目究竟是什么

ScholarHarness 是本地优先的 Python 文献研究 Agent harness：用一个可替换的 Runtime 接口承接 Pi RPC 或教学用 MiniPy；在 Runtime 外统一管理文献、工具、可信记忆、可回放 Trace 和确定性 Evaluation。它不是训练大模型的项目，也不是已经上线的多租户 Agent 平台。浏览器里的可拖拽会话图目前投影的是 MiniPy 持久会话，并非 Pi 原生 UI。README · 架构说明

已实现

两条 Runtime 路径

Pi 通过子进程 JSONL RPC 接入；MiniPy 在 Python 中显式运行模型—工具循环。两者遵守同一个 AgentRuntime 契约。

教学价值

可见的 Agent 机制

在 MiniPy 中可逐行追问：上下文何时注入、模型为何再调用、工具参数如何校验、Abort 如何取消、分支怎样选路径。

边界

本地作品集，而非 SaaS

网页不具备公网多用户身份体系；扫描 PDF 尚无 OCR；离线 hashing 向量不是高质量语义模型；Pi 原生图形会话未接入网页。

面试的第一句：“我没有把 Pi 二次开发误称为全部 Agent 能力。Pi 负责成熟运行时；我在 Python 侧重点实现领域 harness 和可检验边界，再用 MiniPy 作为透明参考实现。”
能力实际状态怎么证明
Pi RPC 与 TypeScript bridge已实现，独立运行路径pi_rpc.py、index.ts、pi-smoke
网页 Agent 对话及分支图MiniPy 会话；可拖动、缩放、保存视图chat_sessions.py、turn_graph.py、workbench.py
文献 RAGFTS5 + 离线 hashing 向量 + RRF；非神经语义检索papers/repository.py、embeddings.py

02 · 所有权比框架名更重要

系统架构与模型位置

“模型架构”在本项目中指模型接入与 Agent 系统架构，不是 Transformer 内部层或训练图。MiniPy 的 ModelAdapter 将内部消息映射为 OpenAI-compatible Chat Completions 的 messages/tools/tool_choice；真正的模型在外部服务，项目不训练或托管权重。model.py · openai_compatible.py

Runtime 拥有什么

活跃上下文、模型循环、工具调用调度、Abort、Fork、Compaction、会话 entry。Pi 自己管理 Pi session；MiniPy 管理自己的 append-only tree。AgentRuntime

Harness 拥有什么

文献与引用坐标、工具 schema/验证、记忆信任审查、归一化 Trace、可重复 Evaluation、浏览器 MiniPy 快照及 UI 投影。运行时的内部 session 不被 Python 服务偷偷改写。Ownership rules

为什么两条路径？Pi 让真实 Agent 能力复用；MiniPy 让学习者掌握 loop、状态、工具、安全与测试，而不是只会配置 SDK。两者的共同点由接口与 Trace parity 验证，不表示它们内部实现完全相同。

为什么不能只存聊天文本？

文本串无法恢复 tool-call ID 与 tool-result 配对，无法表示兄弟分支，也无法判断哪些上下文被 compaction 截断。MiniPy 保存完整 entry tree，并在每次模型调用前从 active_leaf_id 逆向回溯父节点、反转成顺序路径；若有 compaction，只取最后一个 compaction 及其之后的 entry。这个设计给“重试旧问题”和“从旧答案继续”提供不同 anchor。_active_path / _model_messages

SQLite 是什么一致性级别？

统一连接策略启用外键、5 秒 busy timeout、WAL、synchronous=NORMAL；每个领域仓库管理自己的事务。会话快照使用 BEGIN IMMEDIATE、先 upsert session、再替换其 entries，最后 commit；异常 rollback。它保证单次 checkpoint 原子，不等于跨文献、记忆、Trace 和外部模型的全局事务。sqlite.py · chat_persistence.py

05 · 从 PDF 到可核对的原文

文献摄取、混合检索与引用

  1. 输入边界：POST /papers/import/pdf 限 50 MiB，要求 PDF 结构；可读文本按页提取，空白页统计为 skipped；全无可提文本则明确报 OCR-required。纸张 ID 默认取内容 SHA-256 前缀。api.py · pdf.py
  2. 切块：默认 1800 字符、重叠 250，优先段落/句号等边界；ID 用 p0001-c0001 式页/块坐标。导入不是复杂版面分析，图表和双栏可能丢语义。
  3. 写入：papers、passages、passage_fts、passage_embeddings。同 paper ID 重导入会替换其 passages/FTS/embeddings；embedding 与 passage 数、维度先验证。repository.py
  4. 词法：FTS5 MATCH + bm25 排名，字段权重在 SQL 中；结果带坐标。查询 token 被转义并用 OR 连接。
  5. “向量”：将词特征与 3/4/5 字符 n-gram hash 到默认 256 维，按 hash 位决定符号，L2 归一化；查询与库存向量做点积并全量排序。这偏词形相似，不是通用语义理解。embeddings.py
  6. 融合：两个排序各取候选（至少 50），同坐标合并：score = Σ 1/(60 + rank)；只在一个列表出现也可命中。RRF 避免直接相加不同量纲的 BM25/相似度分数。返回 lexical_rank/vector_rank 便于解释。
  7. 引用：Agent 应再调用 validate_citation：按 paper/passsage 读取原文，校验 quote 是否属于该 passage。它是片段包含性检查，不保证论证逻辑与论文结论正确。tools.py
追问示例：“为何不用余弦和 BM25 原始分数直接相加？”答：范围、方向和分布不同，归一化很依赖数据集；RRF 只依赖排序，对 baseline 更稳健，但会失去绝对相关性信息，也无法替代重排器。

06 · 记忆是有信任等级的状态

Memory 不是多塞几句 Prompt

候选创建

SaveMemoryInput 的 extra="forbid"，模型只能填内容、kind、scope、confidence 和证据。save_memory 会在指定 passage 中做空白归一与大小写折叠后的 quote 包含校验，再写 candidate。session/entry/run/call 来源由 ToolExecutionContext 注入。models.py · tools.py

自动召回

每轮前 MemoryContextPolicy 搜索 confirmed，允许 global 和同 session 的 session scope，排除 branch scope；默认最多 5 项、4000 字符，记录 retrieved/eligible/selected/omitted/truncated/excluded 数与 ID。内容明确标成“参考数据而非指令”。失败会有 context_injection:error 观测。context.py

Supersession：替换不是覆盖旧内容。确认过的旧记录可以显式指向另一个活跃 confirmed 记录；kind、scope、所属 session 必须匹配，拒绝链式替换，旧记录改为 superseded 留审计。召回只搜索 confirmed，因此不会把旧结论和新结论同时注入。memory/repository.py

信任仍有限：quote 出现在 passage 中不意味着 memory 的推论正确；被检索文档也可能含 prompt injection。当前策略把记忆标为数据并要求引用核验，但没有完整的沙箱、内容分类或人工科研事实审查。

07 · 分支不是复制会话

Append-only Session Tree 与图形投影

MiniPyRuntime.fork(entry_id) 只校验 entry 存在并修改 active leaf；下一条 append 的 parent 指向这个 leaf。project_turn_graph 找 user message 与最近 user 祖先，聚合本轮 assistant/tool，生成 continue_entry_id、other_answers 和该节点祖先路径的 messages。点击节点只是读 UI；“从此继续” fork 到该轮结束 anchor；“重试此轮” fork 到用户问题 ID。mini_py.py · turn_graph.py · workbench.py

每个 turn 结束及 fork/compact 后会 checkpoint 完整树。重启时先列出轻量 snapshot 摘要，真正连接时才懒加载 Adapter 并验证树；损坏的 parent/leaf 不被悄悄接受。图节点拖动位置与 zoom/pan 只是浏览器 localStorage 中按 session ID 保存的视觉偏好，不是 SQLite 会话数据。chat_sessions.py · chat_persistence.py

PiX 差距：当前浏览器只有 MiniPy 的单会话分支图与路径预览；它不等于 Pi 原生多列并行 Agent 工作区，更没有声称独立并行执行分支。用户若问“复制 PiX 了吗”，应明确回答“尚未”。

08 · 先记录证据，再评价行为

Trace → Evaluation → Suite → CI

TracingRuntime 包装任意 AgentRuntime，创建 run，按序记录 event，并关联 tool execution；ContextVar 绑定当前 run，使并发任务的 provenance 不串线。稳定 session entries 使用幂等键投影，live delta 另存以保留重放粒度。TraceSanitizer 递归按 key 名脱敏，默认超过 256 KiB 的 payload 只留预览。runtime.py · redaction.py

TraceEvaluator 对完成/失败/中止的终态 run 做可解释规则检查：必需/禁止工具、调用次数、耗时、有效 validate_citation、终态、答案包含、Memory context 状态/ID/数量。每条 check 保存 expected 与 observed；分数是通过 check 数/总 check 数，passed 由 case 阈值决定。与同 case 的上一个不同 run 比较出 delta 和 regression。注意 regression 在代码中是分数下降，不等于一定低于 pass threshold。service.py

执行 Case 时创建独立 MiniPy session，走正常 Trace，再评测，最后清理临时 session；Suite 按有序 case 顺序执行，单项编排错误以安全类别记录并继续。结果快照不随 case 后续编辑变化。eval-gate 从持久化 suite run 输出 JSON/JUnit：0 全通过、1 质量失败、2 配置或运行错误。runner.py · suites.py · CI 文档

Pi/MiniPy parity：比较终态、生命周期事件、工具名/错误结果、Memory context 状态与是否产生回答；默认忽略 volatile ID、时间和精确措辞，--strict-output 只适合确定性 fixture。这个测试证明公共行为契约，不是证明模型答案等价。parity.py

评测盲区：有一次成功的引用验证，不意味着最终回答的每一句都引用正确；检查了 answer substring，不代表语义正确；确定性检查不能替代专家核查与有标注样本的检索质量评估。

09 · 信任边界与故障模式

安全不是“有个 API Key”

威胁 / 失败当前防线仍需诚实承认
模型伪造 Memory 来源模型 schema 无 session/entry/run/call ID；由 immutable ToolExecutionContext、task-local run binding 或 Pi bridge header 提供。context.py共享密钥只保本地 Pi provenance 路径；公网仍需用户级授权与进程/网络隔离。
伪造 Pi bridge header配置 SCHOLAR_HARNESS_BRIDGE_TOKEN 时，带 provenance 的 HTTP tool call 在工具执行前做常量时间比较。api.py未配置 token 是本地零配置模式；不是公网默认安全模式。
Trace 泄漏敏感字段递归对 secret-like key 脱敏并限制 payload 大小。redaction.py按 key 的脱敏不能保证 prompt 正文里没有秘密；需扩展内容级检测与访问控制。
Prompt injection / 错误 Memory只注入 confirmed，声明“参考数据非指令”，证据坐标、人工确认及长度预算。context.py不能数学上保证模型不听数据中的恶意指令；需权限最小化、测试集和人工审查。
恶意 / 巨大 PDF50 MiB 限额、文件头/PDF 结构检查、无法提取则拒绝。api.py没有扫描件 OCR、恶意文件沙箱、复杂版面理解。
并发 SQLite 写冲突WAL、5 秒 busy timeout、外键、事务/回滚；会话 checkpoint 使用 BEGIN IMMEDIATE。sqlite.py单机适用；多实例高写入量应改 PostgreSQL/队列。
浏览器 XSS / Key 暴露Workbench 用 textContent / safe DOM、CSP 且无外部资产；Key 只留在 API 进程。workbench.py当前 CSP 允许 inline script/style，适合本地 demo；公网需收紧 CSP、CSRF/CORS 和登录。

错误处理也有边界：模型 HTTP 适配器将网络/协议/非 2xx 错误归为安全类别并遮盖已知 Key/URL；Chat 恢复时区分配置缺失与损坏 session；Abort 是合作式取消，不等于立即撤回外部已发生的副作用。openai_compatible.py · chat_sessions.py

Ⅰ. 项目架构和真实边界

01｜30 秒介绍：你到底做了什么？

我做的是 Python 文献研究 Agent harness，而不只是聊天页：上层可接 Pi RPC 或自写 MiniPy；中间统一 ToolRegistry、可信 Memory、Trace；下层以 SQLite 管文献与会话；再用 Case/Suite 评测运行行为。最核心的取舍是 Runtime 与领域逻辑分开，使工具和评测不绑死于一个 SDK。

源码：runtime contract · ownership

02｜为什么同时做 Pi 和 MiniPy？这不是重复造轮子吗？

目标不同。Pi 复用成熟的会话与工具调度，降低真实运行成本；MiniPy 约束在小而透明的 Python loop，用于解释、测试 tool calling/abort/branch/compaction 和做可控 fixture。业务逻辑只写在 Python 工具/Memory/Trace 层，不把两套领域规则复制到 TS。共同契约的行为用 trace parity 逐项比较，而不是声称两个 Runtime 内部等价。

追问：若删掉 MiniPy，学习成本和离线可测性下降；若只留 MiniPy，真实 Runtime 的稳健性要自己承担。

MiniPy · Pi RPC · parity

03｜为什么 Runtime、ModelAdapter、ToolRegistry 要分三层？

ModelAdapter 只翻译模型请求/响应；Runtime 负责多轮控制流、状态、工具调度、取消和分支；ToolRegistry 负责可见 schema、参数验证与业务执行。三者是不同变化轴：换模型不改会话树，换运行时不改证据规则，换工具不改 HTTP provider。这样的依赖反转也让 fake adapter 与工具可独立测试。

追问：若 ModelAdapter 直接调用工具，无法在运行时统一实施轮次上限、Trace 和 provenance。

ModelAdapter · ToolRegistry

04｜网页的 Agent 对话是不是 Pi？能否与 PiX 等同？

不是。网页创建的是 server-owned MiniPy session，由 OpenAI-compatible Adapter 连接模型；Pi 是另一个 pi --mode rpc 子进程路径。网页图显示 MiniPy 的 user-turn 投影，支持节点拖动/缩放、历史路径与显式 fork/retry，但不是 Pi 原生多列并行工作区，也没有宣称复制 PiX 的全部效果。这一事实必须在面试中主动说明。

追问：若要 Pi 原生图，需以 Pi 的 session entry/branch 语义为服务端权威源、设计 reconnect/并行任务和冲突处理，而非只改前端。

chat_sessions.py · workbench.py

05｜双 Runtime 如何做到“不维护两套业务逻辑”？

Pi extension 不保存文献/Memory 算法，只把注册的工具调用通过 localhost HTTP 转给同一个 Python ToolRegistry；MiniPy 则直接调用 Registry。文献检索、引用校验、记忆候选验证都是 Python 的单一实现。仍需维护两份工具“声明外壳”——TS 的 Pi 注册 schema 与 Python Pydantic schema，存在漂移风险；当前用 smoke/test 缓解，进一步可生成 schema 或合同测试。

追问：单一业务实现不等于完全消除双语言维护。

Pi extension · registry.py

06｜什么是 Harness？与 Agent 框架有何不同？

本项目中的 harness 是运行时周围的一组约束和支持系统：工具、数据、Memory 信任、Trace、Evaluation、会话保存及操作界面。Agent 框架/Runtime 着重决定“模型何时看到上下文、何时调用工具、何时停止”；Harness 着重决定“工具能访问什么、结果如何核查、发生了什么、能否回归测试”。边界不是行业统一定义，但这是本仓库的明确 ownership。

追问：换 LangGraph/Pi/自研 loop，哪些部分可复用？本项目答案是工具、文献、Memory、Trace 语义和 Case/Suite。

architecture.md

07｜为什么 WebSocket 只传指令，不把模型配置放浏览器？

浏览器是低信任展示层，若接收 provider URL/Key，用户误操作或 XSS 可泄漏；服务端统一建 Adapter，浏览器仅传 prompt、abort、compact、fork、entries。WebSocket 用于命令与事件双向流；REST 用于创建/列出/删除 session 及读 graph。控制面和数据面分离也让重连、错误码与权限边界更清楚。

追问：这不自动带来多用户安全；本地单用户假设必须说明。

api.py · chat_sessions.py

08｜Pi JSONL RPC 如何同时处理请求响应和异步事件？

每个命令分配 request ID，pending map 持有 Future；stdout 读取任务逐行 JSON 解码，type=response 且 ID 命中就 resolve 对应 Future，其他消息入事件队列。因而等待 get_state 或 prompt 的响应不会吞掉未请求的模型/工具事件。进程退出或坏 JSON 时要 fail 所有 pending Future 并终止事件迭代。

追问：超时清理 pending、防重复 ID、stderr 只保留尾部；这是异步协议健壮性的核心，不是简单 subprocess.run。

pi_rpc.py

09｜你如何证明 Pi 与 MiniPy 功能一致？

不能证明“完全一致”。当前 parity 从持久化 Trace 投影双方终态、生命周期顺序、工具名与错误、Memory context 状态、是否有回答，再比较；默认不比较时间、ID 或原文，以避免非确定性与 chunk 差异。严格输出只用于确定性 fixture。这检验公共可观察契约，模型质量、内部 token 处理和并行行为还需额外评测。

追问：若 parity 失败，应先判断是规范化投影差异、运行时语义差异，还是模型非确定性。

parity.py

10｜为何“本地优先”不等于“生产就绪”？

本地优先意味着 SQLite、单机 API、可离线 benchmark、无 Key 测试、浏览器本地管理。公网生产还要身份/租户隔离、TLS、密钥托管、审计访问控制、限流、CSRF/CORS 策略、后台队列、灾备和数据库迁移。项目已经做了桥接 token、脱敏、WAL/事务等生产意识，但不能用这些替代完整平台安全。

追问：怎么迁移？先抽象用户/租户上下文，再将 repository 移往 PostgreSQL，耗时任务入队，并重新设计授权。

Ⅱ. Agent Loop、Tool Calling 与上下文

11｜一个最小 Agent Loop 的状态机是什么？

输入 prompt 与当前活跃路径 → 组装 messages/tools → 模型返回 assistant 内容和可选 tool calls → 校验并执行每个工具 → 将 tool result 追加为消息 → 继续问模型，直到无 tool call、达到最大轮次、失败或 Abort。关键不在 while True，而在可观察的边界：轮次上限、错误如何回填给模型、哪些结果持久化、取消是否传播。

追问：本项目默认上限 8 个“工具轮次”，不是 8 个单独 tool call。

MiniPyRuntime.stream

12｜Tool Calling 与“模型执行 Python 函数”有什么本质区别？

模型只输出结构化的“调用意图”（工具名、参数、call ID）；Runtime 决定是否接受，Registry 用 Pydantic 验证参数，再在受控代码中执行并返回结果。模型并没有 Python 执行权限。这个边界允许拒绝未知工具、阻断多余字段、记录调用上下文并实施超时/取消。

追问：格式合规不代表授权合规；还要在 tool handler 中检查权限、数据范围和副作用。

registry.py · model.py

13｜模型一次返回多个 tool calls，项目会并行执行吗？

MiniPy 当前按返回顺序逐个执行，并逐个发 start/end event、追加 tool message；没有默认并发。顺序执行更易保证 trace 顺序与副作用可读，但增大总延迟。若改并行，需定义工具依赖、结果消息顺序、部分失败/取消、共享数据库写冲突与 provenance 的任务隔离。

追问：可并行的前提是工具幂等且相互独立；不能只把 for 改成 gather。

mini_py.py

14｜Abort 真的能中止外部模型和工具吗？

MiniPy 用 abort event 与正在进行的 awaitable 竞争；Abort 胜出则取消 operation task 并等待收束，终态为 aborted。这个行为是合作式取消：异步 HTTP 通常可取消等待，但外部服务或已提交的数据库写不保证回滚。要更强保证，应给副作用工具设计幂等键、状态检查、补偿和超时。

追问：取消与超时不同；取消来自用户意图，超时来自资源预算，两者的审计原因应分开。

_interruptible · tests

15｜Compaction 在这里是不是 LLM 自动摘要？

不是。当前 MiniPy compact 遍历活跃路径的文本，拼成 role/content，超过字符预算时截取尾部，可加用户 instructions，然后追加一个 compaction system entry。模型下次只看最后 compaction 及之后的路径。这是透明但粗糙的教学实现，不是语义摘要；可能丢掉早期事实或证据。

追问：生产方案要有引用保真、重要事实保留、摘要质量评测、token 预算而非字符预算。

compact / _model_messages

16｜System/Developer/User/Tool 消息的信任等级如何看？

一般原则是高优先级策略与低优先级数据分开；用户输入、文献正文和工具返回都可能包含恶意指令，不能因“被检索”就升级成系统规则。本项目把 confirmed memory 渲染成 system entry 但明确写“参考数据、非指令”；这是缓解措施，不是数学隔离。更严格的方案会在协议层区分来源并对敏感工具做授权。

追问：系统消息承载未可信文本本身就是风险，必须解释为什么还需要人工确认和后续核验。

context.py

17｜为什么要有 ToolExecutionContext，不能把 session_id 放进函数参数 schema？

函数参数 schema 是模型可见、可生成的；若把来源 ID 放进去，模型就能伪造 provenance。Runtime 持有 session、entry、call，TracingRuntime 用 ContextVar 绑定 run，Pi extension 从只读 ctx 取 session/leaf 并走专用 header。handler 接收不可变 context，模型只能提出业务参数。

追问：header 也能被普通 HTTP 客户端伪造，所以配置 bridge token 时必须先验证再构建 context。

context.py · api.py

18｜为什么 tool result 要回填到模型上下文，同时也进入 Trace？

回填上下文是下一轮推理的因果输入：模型必须看到检索/验证结果才能继续。Trace 则为外部观察与评测保存“实际调用过什么、是否错误、返回了什么”的证据，两者生命周期不同。只存 Trace 不回填模型，Agent 无法利用工具；只回填模型不存 Trace，就无法回放、审计或做 deterministic evaluation。

追问：Trace 需脱敏，不能默认与模型上下文或用户权限相同。

mini_py.py · runtime.py

19｜“实时输出”与“模型流式输出”如何区分？

浏览器 WebSocket 能实时收到生命周期、Memory、工具事件；Pi RPC 路径可以接收 Pi 的异步事件。MiniPy 的 OpenAI-compatible Adapter 当前对 /chat/completions 做普通 POST，不设置 stream，响应结束后才发一次完整内容的 message_update。因此不能把网页 WebSocket 的存在说成逐 token streaming。

追问：要真流式，Adapter 需解析 SSE/token delta，同时处理工具调用参数增量拼接、取消与断线重连。

openai_compatible.py · mini_py.py

20｜模型供应商可替换，真的“provider-neutral”吗？

内部 ModelAdapter 是 provider-neutral 接口，但当前具体实现是 OpenAI-compatible Chat Completions，要求供应商兼容其 message/tool-call 形状。换兼容供应商只需配置 URL/model/key；换完全不同协议需新 Adapter。Runtime 不依赖特定供应商，但不是无条件支持任意模型。

追问：工具 schema、JSON 兼容性、上下文限制、错误语义和 token 统计仍可能因供应商不同而变化。

model.py · openai_compatible.py

Ⅲ. 文献 RAG、检索和引用八股

21｜RAG 的基本链路是什么？本项目具体实现到哪里？

理论链路是摄取→切块→索引→召回→融合/重排→把相关证据放入模型上下文→生成→校验。这里实现数字 PDF 按页切块、SQLite FTS5 和 hashing 向量索引、RRF 融合、paper/passage/page 坐标、读取 passage 与 quote 包含性验证。没有 OCR、复杂版面解析、专用 embedding、ANN、cross-encoder 重排或端到端事实判定。

追问：不要把“有向量字段”当作已经具备高质量语义 RAG。

pdf.py · repository.py

22｜BM25 是什么？为什么 FTS5 的排名不能直接当概率？

BM25 是基于词项频率、逆文档频率和长度归一化的相关性函数；SQLite FTS5 提供 bm25(...) 排序，当前代码对返回 rank 取负作为展示 score。它是相对排序分数，不是“答案正确概率”，会受分词、字段权重、语料规模影响。中文分词质量尤其应单独评测。

追问：为什么检索和引用分开？高分只代表检索相关，不能证明引用原文存在或推论正确。

_lexical_search

23｜HashingEmbeddingProvider 是“语义向量”吗？

它是确定性离线 baseline：token 与字符 n-gram 经 blake2b 映射到 256 维、按某位给正负号、最后归一化。对词形相近或共享 n-gram 有帮助，但没有通过语义训练学到同义关系；不同表达可能无法对齐，还存在 hash collision。好处是无外部依赖、可复现、可用于测试接口和混合检索流程。

追问：换神经 embedding 时还要规划 provider/version、旧索引重建、维度兼容和离线评测。

embeddings.py

24｜为什么向量相似度是点积？什么时候等价余弦？

当前 hashing 向量生成后做 L2 归一化，因此两个非零向量的点积等于余弦相似度。零向量单独跳过，存储向量维度和字节长也要检查。这个结论只对已归一化向量成立；换 provider 若不保证归一化，点积与余弦不再等价。

追问：代码使用 Python 遍历所有匹配 provider 的向量计算点积，时间随 passage 数线性增长。

embeddings.py · _vector_search

25｜RRF 公式、优点、局限是什么？

对每个候选 passage，RRF(d)=Σ 1/(k+rankᵢ(d))，本项目 k=60；分别从 lexical 和 vector 候选列表加分。不要求把 BM25 与余弦值校准到同一标尺，且缺席一个列表的候选仍能留下。代价是忽略原始分数和绝对置信度；若一个召回器质量很差，仍可能引入噪声。

追问：改善应先做离线标注集的 Recall@k/MRR/nDCG，再调候选数、权重或加 reranker。

search

26｜Chunk size 与 overlap 为什么不是越大越好？

大块保留跨句上下文但检索定位变粗、上下文成本高；小块定位精确但可能切断论证与引用。Overlap 可降低边界截断，却增加存储和重复命中。当前默认 1800/250 字符并优先句子边界，适合可复现 baseline；不是按 token、标题层级、表格结构优化的学术 PDF 分块。

追问：页码必须在块形成前保留；跨页混块会破坏精确引用坐标。

PdfIngestor

27｜为什么 citation validation 只做 quote 包含，不检查答案真伪？

坐标和原文逐字包含是可确定性验证的事实；“这段话是否支持结论”需要语义/科研判断，单纯 substring 无法覆盖否定、断章取义或引用错位。本项目将基础坐标验证放在工具层，保留 Trace 供人工/更高级评测检查，而不夸称 citation tool 能解决幻觉。

追问：可增加句子级 claim-evidence entailment 与人工抽检，但其误判率需要标注集测量。

validate_citation

28｜重导入同一个 paper_id 时会发生什么？

Repository upsert paper 元数据，然后删除该 paper 旧 passages/FTS 条目，再批量插入新 passages、FTS 与 embeddings；表的外键负责关联清理。这样索引不会与正文漂移，但旧引用坐标可能失效。生产系统应引入文献版本、内容 hash、增量索引和引用快照，不应默默让审计过的 evidence 指向变化的内容。

追问：旧 Memory 引用的 paper/passage ID 如果同名内容被替换，是潜在一致性风险。

SQLitePaperRepository.add

29｜如何评测 RAG，而不是只看模型最终回答？

把链路拆开：摄取质量（抽取/页码/版面）、检索质量（有标注答案 passage 的 Recall@k、MRR、nDCG）、引用质量（坐标准确率、claim 支持率）、生成质量（事实性和遗漏）、成本/延迟。当前 benchmark 测程序吞吐与坐标有效性，Evaluation 测工具行为；尚没有完整学术事实标注集，不能把 100 次 benchmark 查询当 retrieval quality 证明。

追问：离线真实标注集要包含难例、同义改写、跨段证据和诱导性无答案问题。

benchmark.md · service.py

30｜为什么做混合检索，而不是仅向量或仅关键词？

关键词路径对术语、精确实体、页内引用敏感；向量路径可以提供另一种相似性信号。当前 hashing baseline 的语义增益有限，但架构上允许更换 provider，RRF 则保留两个检索器的可解释 rank。混合并非必然优于单路，要用真实查询集证明收益；否则复杂度和重复候选可能只是负担。

追问：本项目支持显式 mode=lexical 做对照，不应只展示 hybrid 的好例子。

search

Ⅳ. Memory、分支与信任

31｜Agent Memory 与普通 RAG 检索有什么区别？

RAG 的原始来源是外部文献；Memory 是系统从过往运行中提炼的可复用状态，需决定 kind、scope、信任和失效。两者都能进入上下文，但 Memory 更容易形成自我强化错误：模型错误总结→再次召回→被当作既定事实。所以本项目要求 evidence-backed candidate、人工确认、明确 supersession，并在注入时保留文献坐标。

追问：Memory 不是无限扩展 context；预算和时效管理是必须的。

context.py · tools.py

32｜semantic/episodic/procedural memory 怎么区分？项目是否全实现？

理论上 semantic 是事实/概念，episodic 是具体经历/事件，procedural 是步骤/方法。项目的 Memory model 支持这三种 kind，并让候选记录带 kind；但当前召回主要用 confirmed 状态与文本搜索，并没有为每种 kind 建独立的编码、衰减或行为策略。因此说“支持分类字段”，不要说“完整认知记忆系统”。

追问：若要 procedural memory 可执行化，必须先审查来源、权限与版本，不能把文本步骤自动变成高权限命令。

models.py

33｜为何 candidate 不能自动确认？

Agent 提议的记忆即便 quote 存在，也可能是断章取义或时效性错误。candidate 是模型可写的低信任区；confirmed 是后续自动召回的高信任区，两者之间应有人工/审查动作。Repository 只让 confirmed 进入 search_confirmed，rejected/superseded 仍保留审计。这个状态机把“模型可以写”与“系统相信它”明确分开。

追问：大规模自动审核可辅助人，但必须量化误确认成本；高风险领域仍需要人。

repository.py

34｜Memory scope 的 global/session/branch 是怎样生效的？

模型可请求 scope，但 session/branch 候选必须有 runtime 提供的 session provenance。自动 pre-turn recall 允许 global 和与当前 session_id 相同的 session；branch 当前被排除，因为 Pi/MiniPy 尚无统一持久 branch identity 策略。数据库有 branch 字段不等于 branch 自动注入已上线。

追问：需要定义 branch 创建、继承、合并、失效和跨 Runtime 映射后才能安全放行。

memory/tools.py · context.py

35｜MemoryContextPolicy 的预算控制有什么细节？

从 confirmed 搜索最多 50 个候选，过滤 scope 后按顺序取默认最多 5 项，组装带 ID/来源坐标的参考数据块，总字符默认不超 4000；如果第一项过长，会截断它，后续项可能被舍弃。Trace 记录选中 ID、检索/资格/省略/截断/排除数量。这是字符预算而非 token 预算，且没有语义去重。

追问：生产改造可按 token 精确预算、效用得分与相似度去重，并记录被排除原因。

36｜记忆替换为什么是 supersede，不直接 update 旧文本？

直接 update 会抹掉旧证据与历史推理的可追溯性；supersede 将旧 confirmed 指向新的 active confirmed，旧内容仍可审计但不再召回。Repository 要求 kind、scope、session ownership 相同并拒绝替换链，避免“旧→新→再新”的歧义。它解决版本替换，不自动解决事实冲突检测。

追问：若要跨文献时效性更新，须加入有效期、冲突检测与审查 UI。

37｜点击旧节点、从此继续、重试此轮，有何区别？

点击只改变网页选中节点和预览 transcript，不改变 active leaf。继续将 active leaf 指向该轮结束的 continuation entry，下一条问题继承旧回答与工具结果。重试将 leaf 指向该轮 user message，新回答成为兄弟分支，不继承旧回答；旧回答保留作审计。三者都不删除历史 entry。

追问：图节点是 user-turn 聚合，不是 session entry 本身；正确 anchor 由投影生成。

38｜重启后会话怎么恢复，如何拒绝坏数据？

每轮及树变更后保存 session 元数据与完整 entries；列表读取只取摘要，连接时懒加载实际树/Adapter。MiniPy 恢复校验每条 entry 属于当前 session、ID 非空且唯一、父节点已在此前出现，非空树必须有存在的 active leaf。坏数据被明确拒绝，不用“尽量修复”掩盖上下文不确定性。

Ⅴ. Python、数据库、Web 与安全八股

41｜async/await 为什么适合这里？哪里不适合？

Pi 子进程读写、模型 HTTP、WebSocket 与等待工具响应都是 I/O 密集，asyncio 让一个线程在等待期间处理其他连接。它不自动加速 CPU 计算；当前 Python 全量向量扫描和 PDF 解析会占 CPU，库变大后应考虑进程池、专用索引或后台队列。任何在事件循环中直接长时间运行的同步操作都可能拖慢其他会话。

追问：Pydantic/SQLite 某些同步调用在 async handler 中仍会阻塞，要量测并迁移重活。

42｜Protocol 和 ABC 在这个项目各有什么用途？

AgentRuntime 用 ABC 明确必须实现的生命周期与 async 方法；ModelAdapter、EmbeddingProvider 用 Protocol 表达结构性契约，便于 fake/stub 或不同实现按能力接入。ABC 更强制显式继承和实例化检查，Protocol 更灵活但运行时约束主要靠类型检查/测试。选择取决于是否需要共同基类行为与显式身份。

43｜ContextVar 为什么比全局变量适合 trace_run_id？

异步服务中多个 turn 可能在同一线程交错执行，模块级全局 run_id 会相互覆盖；ContextVar 随当前异步任务上下文传播，绑定时保存 token，退出时 reset，能让工具执行读取本次 Trace 的 run ID。它不是身份认证，仍需要可信入口设置且避免跨进程误用。

追问：在新建后台任务、线程池或进程池时要审视上下文传播规则，不能假设所有边界都自动保真。

44｜Pydantic 校验与 JSON Schema 解决了哪些问题，没解决什么？

同一输入 model 可暴露工具参数 schema，也能在执行前验证类型、长度/范围和额外字段策略，减少模型乱填参数导致的异常。但 schema 只保证形状，不保证用户有权读某论文、quote 支持结论或保存记忆符合业务政策。业务约束仍放在 handler/repository，权限上下文必须来自模型不可控通道。

追问：TS Pi 工具 schema 与 Python Pydantic schema 双维护，合同漂移需要测试。

45｜SQLite WAL、busy_timeout、BEGIN IMMEDIATE 各解决什么？

WAL 使读与单写者在常见情况下并行，busy_timeout 给写锁竞争有限等待，外键维持引用完整性；BEGIN IMMEDIATE 在事务开头尝试保留写锁，避免做了半套业务才发现无法写。它们仍不能让 SQLite 同时有多个写者，也不保证外部模型调用与数据库写处在同一原子事务。

追问：synchronous=NORMAL 是性能/耐久权衡；断电语义与 full fsync 不同，需依据业务风险选择。

46｜事务原子性和“端到端 Exactly Once”为什么不同？

会话 checkpoint 的 SQLite 事务可保证同一次保存不会只写 session 不写 entries；但 WebSocket 重试、模型收费请求、工具 HTTP 调用、外部副作用跨越了数据库边界，不能由 SQLite 一次 commit 覆盖。若要求至少一次传输下的逻辑只执行一次，需要幂等 key、去重表、状态机与补偿。当前项目对稳定 entry ingestion 做幂等投影，但不宣称整个 Agent turn exactly once。

追问：失联前模型响应成功但本地还没 checkpoint，是典型不确定窗口。

47｜REST 与 WebSocket 为什么混用？断线怎么办？

追问：真正的断线续流需事件序号、ACK/重放窗口与后端运行与客户端连接解耦。

51｜为什么不能仅凭“模型回答看起来不错”评估 Agent？

回答文本会掩盖错误过程：可能没用文献、调用了错误工具、未验证引用、注入了错误 Memory，甚至答对只是碰巧。Trace 捕获过程，Case 将必需/禁止工具、终态、引用验证和 Memory 选择变成可复现规则。仍要结合人工事实核查，因为行为合规不等于结论正确。

追问：质量维度至少包括任务成功、证据正确、成本/延迟和安全，不应只给单一 pass rate。

52｜Case 分数是怎么计算的？regression 代表什么？

每个配置的预期生成一个或多个 EvaluationCheck，score=passed_checks/total_checks，结果是否通过由 score ≥ pass_threshold 决定。若前一个不同 run 的同 case 分数更高，则 score_delta<0 标记 regression。多个工具要求可各形成一个 check，所以“权重”隐含为每 check 等权；这不等于业务影响等权。

追问：可改成显式权重/严重度，但必须防止调分掩盖关键安全失败。

53｜Evaluation 为什么只读已落盘 Trace，不再跑一次模型？

将执行与评价分离，能对同一 run 用不同 Case 复评，避免模型随机性和额外费用；结果也可追溯到当时的事件与工具输出。自动执行 Case 是另一层 EvaluationRunner，它先创建独立 session 跑 prompt，再交给 TraceEvaluator。两者职责清楚：执行产生证据，评价解释证据。

追问：只读历史 Trace 意味着新规则可能缺少历史未记录字段，观测 schema 要有版本策略。

54｜如何评价自动注入的 Memory，没有重新检索造成“当前状态漂移”？

Trace 中每轮有一条 context_injection，记录状态、selected IDs 和数量；Evaluator 从当时的事件投影观察值，不查询现在的 memory repository。要求恰好一条有效 event，缺失/重复/字段无效则检查失败。这样历史评测不受后来 confirm/supersede 变化影响，且不把记忆正文复制进结果。

56｜CI gate 的 0/1/2 退出码有什么价值？

Ⅶ. 大模型基础八股：理论延伸，不是本仓库模型实现

下列问题帮助应对 Agent 岗位的模型基础追问。ScholarHarness 通过外部 Chat Completions API 调模型，没有实现 Transformer 训练、推理服务或 LoRA 微调；请把“我理解原理”与“我在项目里实现了”分开说。参考原始论文：Transformer、RAG、LoRA。

61｜Self-attention 的 Q/K/V 与缩放点积公式？

输入表示经三组线性变换得到 Q、K、V；每个 query 与各 key 点积得到相关性，除以 √dₖ 减缓维度增大导致 softmax 饱和，再经 softmax 作为对 value 的权重：Attention(Q,K,V)=softmax(QKᵀ/√dₖ)V。多头 attention 让模型在不同投影子空间捕捉关系。因果语言模型还需要 causal mask，避免看见未来 token。

追问：注意力权重不是严格的因果解释；项目本身并未实现 attention。

理论来源：Attention Is All You Need

62｜Transformer 为何需要位置信息？

纯 self-attention 对输入顺序没有天然的序列位置感；位置编码或位置嵌入把“第几个 token、相对距离”等信息带入表示。原始论文使用 sinusoidal positional encoding，现代模型可能采用不同方案，不能把某一种位置编码说成所有模型固定配置。Agent 开发更应关注长上下文的截断、检索证据顺序与位置偏差。

追问：项目的 compaction 用字符长度，不是模型 token/位置预算，因此可能与真实 context window 错位。

理论来源：Transformer 原论文；项目：compact

63｜什么是 Token、context window，为什么字符数不等于 token 数？

Token 是模型 tokenizer 切分的基本单元，不与字符或词一一对应；中文、代码、数字和特殊格式的 token 率不同。Context window 限制模型一次可接收的 token 总数，通常要给生成结果与工具 schema 留预算。本项目 Memory/compaction 当前按字符数控制，便于透明测试，但可能低估或高估真实模型用量。

追问：生产可引入与具体 model 匹配的 tokenizer，并对消息、工具定义、输出预留和系统开销分别计费。

项目：MemoryContextPolicy · compact

64｜Prefill、Decode 与 KV cache 为什么影响 Agent 延迟？

自回归推理先处理整段输入（prefill），再逐 token 生成（decode）。KV cache 保存历史 token 的 key/value，避免每次解码重复计算全部历史。Agent 每轮工具调用都可能重新把长消息和工具 schema 发给模型，因而 prefill/context 成本与多轮次数会叠加。具体缓存是否跨请求复用由供应商决定，本项目不控制它。

追问：性能优化不能只看生成速度，还要看工具往返、检索和长上下文传输。

项目观察点：model loop · adapter

65｜Temperature、top-p 与可复现性如何影响 Eval？

Temperature 调整采样分布的尖锐程度，top-p 从累计概率截断候选集合；它们影响输出多样性，但设置很低也不保证跨模型版本、服务端实现和并发路径完全确定。项目因此主要做 Trace 上的确定性行为检查，parity 默认只比较是否有回答而非文本完全一样。要评测事实质量应控制模型版本、采样参数和数据集，并记录方差。

追问：当前 ModelAdapter 代码没有完整的采样参数控制面，不应声称它已做 deterministic decoding。

项目：parity · adapter

66｜RAG 与 Fine-tuning / LoRA 什么时候选哪个？

RAG 适合频繁更新、需要可追溯来源的外部知识；微调/LoRA 更偏行为、格式或领域表达习惯的参数适配，不能替代实时文献引用。LoRA 的核心是冻结基础权重，只训练低秩更新矩阵以减少可训练参数。ScholarHarness 只实现 RAG/harness，没做 LoRA；若面试官问选型，应先定义错误是“没找到知识”还是“模型不会按规则使用知识”。

追问：两者可组合，但要各自测量检索召回与生成行为，避免把数据质量问题拿微调硬补。

理论：RAG 论文 · LoRA 论文

67｜Function calling 是模型“强制遵守 JSON Schema”吗？

模型可能按供应商协议给出结构化调用，但仍可能填错字段、使用未知工具、违反业务约束；本项目 Runtime 解析 ModelToolCall，Registry 再用 Pydantic 校验，handler 做证据和 scope 约束。即使供应商提供“严格模式”，服务端也不能省略授权与校验；模型输出永远不能直接等同可信命令。

追问：失败参数怎样反馈给模型？当前异常会变成错误 tool result 并被 Trace 记录，直到下一轮或上限。

registry.py · mini_py.py

68｜ReAct 与 Plan-and-Execute 跟项目有什么关系？

ReAct 强调在推理/行动/观察之间交替，MiniPy 的模型→工具→观察→再模型循环具备这种执行形态；但项目没有显式输出/解析隐藏推理链，也没有完整 Planner/Executor 双 Agent 架构。Plan-and-Execute 会先形成计划，再由执行器完成步骤，适合长任务但引入计划过时和协调问题。

追问：不要把任何 while-loop 都称为“实现了 ReAct 论文”；应只描述可见的行动—观察模式。

项目：MiniPy loop

69｜Prompt injection、jailbreak 与工具滥用如何区分？

Prompt injection 常发生在低信任内容（文献、工具结果、网页）试图覆盖高优先级指令；jailbreak 通常是用户直接试图诱使模型绕过规则；工具滥用是模型/用户用可用工具做超权限动作。防线分别包括来源隔离、信任标签、服务端授权、最小权限、审批和观测。项目对 Memory 做数据非指令提示及人工审核，对工具 provenance 做可信上下文，但没有完整通用的注入防护。

追问：即使模型按提示拒绝，服务端仍要拒绝越权工具操作；提示不是安全边界。

项目：context.py · context.py

70｜为什么“LLM-as-a-judge”不能替代确定性评测？

LLM judge 能覆盖部分语义/事实维度，但本身受 prompt、位置偏差、模型版本和成本影响；确定性评测更适合工具是否调用、终态、引用验证结果、上下文 ID/预算等可机械观察的规则。理想体系是可确定规则先守底线，语义 judge 和人工标注用于难例，并对 judge 与人工的一致性做校准。当前项目只实现确定性层。

追问：引用验证 tool 成功 ≠ 回答整体正确，所以再加 judge 也必须有人工抽检。

项目：TraceEvaluator

Ⅷ. 压轴场景：现场推演故障与设计取舍

71｜模型给 save_memory 参数塞了伪造的 source_session_id，怎么办？

先说明信任边界：SaveMemoryInput 配置 extra="forbid" 且不定义来源字段，所以额外参数应在 Pydantic 校验阶段被拒。MiniPy 的 session/entry/call 来源由 Runtime 构造 immutable context，run ID 来自 TracingRuntime 的 ContextVar；Pi 的来源由扩展 ctx 转 header，配置 bridge token 时在 API 入口验证。注意：若攻击者已控制同机环境变量或服务进程，以上本地边界不能代替 OS 级保护。

面试官再问“为什么 read_passage 不要求 token？”答：现有设计只对 provenance-bearing bridge call 加校验，默认是可信本机单用户；公网部署需要所有敏感读取的用户级鉴权。

SaveMemoryInput · execute_tool

72｜两个 Agent 同时写 SQLite，Memory 来源会不会串到另一个 Run？

来源隔离与写锁是两件事。ContextVar 隔离各 async task 的 run binding，ToolExecutionContext 带各自 session/entry/call；SQLite WAL 允许常见读写并发但仍是单写者，busy_timeout 给锁冲突最多约 5 秒等待，事务保证单次操作原子。若负载上升可能超时，需有监控/重试策略并确保写操作幂等；不能因为用了 ContextVar 就说数据库并发问题解决了。

进一步可设计并发测试：两个会话同时 save_memory，核对记录的 source_session_id/trace_run_id 与各 run 一一对应。

context.py · sqlite.py

73｜工具已经写入 candidate，用户此时点 Abort，能否撤销？

不能承诺。Abort 协作式取消正在等待的模型/工具任务，但外部副作用若在取消前已 commit，无法靠取消 Future 回滚；Trace 可能看到 tool start/end 与 aborted turn，Memory candidate 可能已经存在。正确方案不是“强制杀掉线程”，而是让可变更工具支持幂等键、显式状态和可审计补偿；对有风险动作加入确认点。

追问：candidate 的低信任状态缓解了后果，因为它不会自动进可信上下文，但仍是持久数据。

_interruptible · save

74｜数据库快照里某 entry 指向不存在的 parent，服务应怎么恢复？

不应猜测父节点或静默丢弃分支。MiniPy 恢复校验 parent 必须已经在此前 entries 中出现、ID 唯一且 session 一致、active leaf 存在；失败抛错，由 ChatSessionManager 报恢复错误，WebSocket 返回 session_corrupt 并关闭。修复应在受控运维路径上备份并诊断，而不是让用户在不可信上下文继续发 prompt。

追问：列表接口仍可展示 stored summary，但真正 hydration 才进行完整验证。

_restore_entries · get

75｜同一 Pi entry 被重复拉取，会不会污染 Trace 或评测？

Repository 为稳定 entry 构造幂等键，在同一 run 下有唯一索引；重复 ingestion 应跳过该稳定 entry。Live delta 不等同稳定 entry，必须保留以准确重放。评测从落盘有序事件与工具执行读证据，因此幂等策略的粒度直接影响“工具调用次数”等观察值；若把不同 live event 错并，会造成误判。

追问：幂等键只在该 run 范围，不保证跨 run 的模型调用 exactly once。

repository.py

76｜用户问“长时记忆”，文章只写“persistent memory”，搜不到怎么办？

先看 lexical tokenization 与 FTS 命中，再看 hashing n-gram 是否共享词形；两者都弱于真实跨语言/同义语义对齐。不能仅把 RRF 系数调大：RRF 只能融合已召回的候选，召回集合没有正确 passage 时它无能为力。应建设中英改写/同义查询标注集，换经过验证的 embedding provider 或查询扩展，再测 Recall@k 与误检。

追问：神经 embedding 仍可能误召回；保留 lexical 路径和精确 citation 坐标有价值。

hashing · search

77｜已经确认的记忆引用的 PDF 被同 ID 重导入覆盖，怎么办？

这是当前设计值得主动披露的一致性风险：PaperRepository 对同 ID 重导入会替换 passages/FTS/embeddings，Memory 保留旧证据坐标和 quote；若 passage ID 重用但内容变了，过去的已验证结论可能失效。稳健改造是文献内容版本/hash 入 evidence、禁止原位覆盖被引用版本，或重导入后重新验证并把失效记忆标记待审；需要迁移和回归测试。

追问：不能只说“外键会处理”，因为证据语义变了而 ID 仍存在。

add · MemoryEvidence

78｜某 Case 依然 passed，却被标记 regression，是 Bug 吗？

不一定。passed 看是否达到阈值，例如阈值 0.7、从 1.0 降到 0.8 仍通过；regression 看与前一个不同 run 相比分数是否下降。两者回答不同问题。排查应看 checks 的 expected/observed 与前次 case 快照，确认是不是规则定义编辑、模型行为变化或 Trace 数据质量问题。

追问：未来若设关键检查一票否决，需与平均分逻辑明确分离。

evaluate

79｜pi-smoke 通过，为什么网页 DeepSeek 对话仍可能失败？

pi-smoke 验证 Pi RPC 与扩展加载；不带 --check-service 时不测 API 工具服务，更不验证浏览器 MiniPy 的模型 Key、供应商网络、模型名或 Chat Completions 兼容性。排查顺序是 doctor/配置→服务健康→chat session 建立→模型 HTTP 错误类别→Trace 终态→工具与 Memory。不要把不同运行路径的 smoke 混为一谈。

追问：--check-service 也只是 HTTP bridge smoke，不等于模型端到端正确。

run_pi_smoke · adapter

80｜Agent 响应慢一倍，你会如何定位？

先分段测：WebSocket 排队/重连、Memory FTS 检索、组装上下文、外部模型 HTTP（首响应与总耗时）、工具调用次数与各工具耗时、SQLite 写锁/checkpoint、前端渲染。Trace 的有序事件和 tool durations 帮助定位哪段拉长；但当前模型 Adapter 非逐 token 流，Trace 不直接给 TTFT，应补专门指标。再按瓶颈改：减少工具轮次、优化检索/向量扫描、连接复用、后台队列或缩小上下文。

追问：只有总耗时没有分位数与负载曲线时，不要直接归因“模型变慢”。
