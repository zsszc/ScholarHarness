# Automated evaluation execution design

## Orchestration

```text
case id
  |
  +-- EvaluationRepository.get_case
  +-- ChatSessionManager.create
  |       `-- MiniPyRuntime -> TracingRuntime -> model/tools
  +-- session.stream(case.prompt) -> count normalized events
  +-- session.info.last_run_id
  +-- TraceEvaluator.evaluate(case, run)
  `-- finally ChatSessionManager.delete(session)
```

`EvaluationRunner.execute(case_id)` returns `EvaluationExecution`, a typed envelope
containing the deterministic result, trace id, event count, optional public runtime
error, and timestamps.

## Failure behavior

The runner reads the case before creating a session, so unknown cases allocate no
provider resources. It consumes the complete runtime stream. If streaming raises,
it records a stable public error category and checks `session.info().last_run_id`.
When a terminal run exists, normal deterministic evaluation continues. If no trace
was created or the trace is not terminal, execution raises
`EvaluationExecutionError`.

Session deletion lives in `finally`. It requests abort, waits for an active turn,
closes the runtime/adapter idempotently, and removes the session from the manager.
Cancellation is re-raised only after cleanup.

## Error disclosure

The response exposes `model_error`, `runtime_error`, or `evaluation_error` categories
rather than raw provider exception text. Run errors are already generated by the
credential-safe model adapter; no base URL or API key is copied into the execution
envelope.

## API and CLI composition

FastAPI reuses its existing chat manager, trace evaluator, and evaluation repository
to construct one runner. `POST /evaluations/cases/{case_id}/execute` accepts no body.

The CLI builds paper/memory tools, trace/evaluation repositories, and the default
environment-backed chat manager over one database. It executes once, prints the
typed envelope as JSON, and always closes remaining sessions.

## Workbench integration

Evaluation Lab adds a secondary execution button beside manual run grading. It is
enabled only when a case is selected, disables during the request, then refreshes
cases/results/runs and Overview before selecting the returned result. Status text
includes the generated run id and event count; runtime failure remains visible while
the deterministic result can still be inspected.

## Trade-offs

Synchronous execution is simple and transparent but tied to HTTP connection
lifetime. It is appropriate for individual personal-harness cases; batch suites and
long-running models will require a durable job queue in a later milestone.
